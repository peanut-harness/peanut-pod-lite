# Design

## Context

见 [proposal.md](proposal.md)。当前已有 `PackagingApp`、目录包检查与 SHA-256、`ProjectPackageStore` 的多版本索引/提交/恢复能力，以及内置插件管理面板的本地包来源、安装计划和运行时管理。Creator Host 账号控制器能读取加密会话、查询订阅和打开 checkout，但没有按产品/操作授权下载的 API；Creator 面板也没有插件创建向导或远程发行目录。

现有 `publish-signed-public-cpm-release` change 计划让 CPM CLI 直接安装 Lite Host/Core。此 change 将首次安装保留给轻量引导入口，后续产品包管理归 Lite 面板，因此实施前必须串行协调旧 change 的产品安装命令、release catalog 与验证任务，不能让两套安装索引并行写入。

## Goals / Non-Goals

**Goals:**

- 在既有共享插件面板集成插件作者向导和插件生命周期管理，复用现有安装事务与包身份校验。
- 让远程 Peanut 发行具备可信发现、完整性校验、兼容判断和可恢复版本切换。
- 将 Pro 权益验证放在服务端，并让 Lite、Pro 与其他 Peanut 插件通过同一生命周期界面操作。
- 允许从正在运行的 Creator 安全管理普通插件；Lite Host 自身更新先暂存，重启后再切换。

**Non-Goals:**

- 不实现任意公网插件仓库或未经信任的第三方发布者目录；在线来源限于批准的 Peanut 发行目录。
- 不在客户端保存签名私钥，不将 Pro 二进制或账号凭据放入公开 Lite 仓库。
- 不改变 Lite 的免费能力边界、Pro 运行时授权边界或 Creator 支持版本画像。
- 不取消 Lite 首次安装引导，也不让该引导承担常规插件更新和版本管理。

## Decisions

### 1. 共享面板分为“开发”和“插件”两类操作，底层共用包模型

在现有插件管理面板中加入创建/打包流程，并扩展在线 Peanut 目录与已安装列表；不新增第二套插件管理器。创建向导调用现有插件契约生成最小工程，打包与本地校验继续经由 `PackagingApp`；用户从面板操作本地包或远程包时，最终都转换为同一安装计划和事务。

备选方案是把开发者工具放进独立 IDE 或命令行，再让管理面板只负责安装。该方案会继续分散用户入口，也难以复用面板中已有的包与运行状态，因此暂不采用。

### 2. 安装管理器协调来源，ProjectPackageStore 仍是当前工程的安装事实

新增远程 catalog/downloader 层负责来源解析、签名验证、兼容筛选、下载和暂存；校验通过后交给现有目录包校验及 `ProjectPackageStore` 原子提交版本、活动索引与回滚。不得另建一份插件当前版本数据库，也不得让面板自己复制目录或改写 `installed.json`。

本地开发包由用户在本机创建或显式选择，不冒充远程已签名发行。面板必须显示来源与身份，避免把本地开发构建显示成已发布版本。

### 3. 远程公开元数据签名，内容按包身份校验

在线来源使用固定产品信任锚验证规范化签名目录；目录记录绑定插件 ID、版本、渠道、Creator 范围、不可变 HTTPS 地址和摘要。目录签名与地址规则在下载前验证，归档摘要与包内逐文件摘要在下载后、提交前验证。拒绝重定向到未批准主机、路径逃逸、符号链接、清单外文件和同版本不同摘要覆盖。

直接复用单一 CPM 信任锚会混淆 bootstrap 与产品发布的权限；因此 CPM 首次安装信任与 Peanut 产品目录信任保持用途分离。旧 release change 若已冻结了产品 catalog 字段，应先比较后复用已有签名协议和测试向量。

### 4. Pro 下载必须先拿到服务端产品级许可

Creator Host 继续用现有安全存储保护 access token；普通订阅状态仍用于显示账号和升级入口，不能作为安装授权。Pro 安装/升级/修复前，Lite 必须重新查询 Pod 服务端并确认返回的权益明确覆盖目标插件；若当前订阅接口无法区分目标产品，则先扩展为绑定插件 ID、版本和操作的服务端授权接口，再开放下载。服务端确认成功后，归档通过认证请求取得；授权拒绝或服务不可用时在写入前关闭操作。不能使用面板缓存的旧订阅快照满足这一步。

认证信息只放在 TLS 请求头或等价的受控传输中，绝不进入 URL 查询、日志、目录缓存或安装索引。授权结果必须能区分 Pro 权益，避免从“订阅 active”推导所有 Pro 包均可安装。

### 5. 使用已有不可变版本目录和 prepare/commit/recover

下载器写入受控暂存区，先验归档摘要，再校验包 manifest 与逐文件摘要。安装器保留旧版本并原子切换活动索引；失败时清理本事务持有的下载/暂存内容，保持旧索引，若恢复不可证明则报告保守状态并停止重试。

当前 Creator 进程正在运行时，普通 Peanut 插件沿用已有运行时停用、卸载和恢复流程。修改 Lite Host 自身扩展文件需要重启时，只允许先准备并验证新版本，重启时做最终切换；不在活动进程中覆盖正在加载的文件。

### 6. 目录和本地作者流程保持离线可用

在线目录失效不应隐藏已安装插件或本地开发操作；缓存的已验证签名发行可显示为旧数据，但不能伪装成最新版本。作者流程允许从模板创建、校验和打包；在线发布不包含在本 change，避免把本地打包权限误当成发布者签名权限。

## Risks / Trade-offs

- [现有 CPM change 与新面板都试图安装 Lite Host/Core] → 实施前协调旧 change，只保留一个产品安装索引写入者；把 CPM 收敛为首次引导/信任入口或明确删除其产品安装职责。
- [Pod 账号服务返回的权益字段可能无法区分目标产品] → 先验证现有服务响应；不足时新增 scoped 授权 API，并以拒绝/超时负向测试证明默认关闭。
- [插件创建功能会生成可执行代码] → 仅写入用户明确选择的空目录，冲突前置检查；本地创建和远程签名发行在 UI 与状态中清楚区分。
- [网络中断或下载内容损坏] → 隔离暂存、流式大小限制与摘要检查；失败保持已安装活动版本。
- [Creator 正加载 Lite Host 时无法安全覆盖自身文件] → 暂存并延后到明确重启阶段切换，启动后检查版本身份和健康状态。
- [过多历史版本占用工程空间] → 版本列表显示占用与活动状态，清理只允许移除未活动且非恢复必需的版本。

## Migration Plan

1. 在开始功能实现前，重审 `publish-signed-public-cpm-release` 的现有 spec delta、候选工作与 OpenSpec tasks，确定 CPM 首次引导和 Lite 产品安装的唯一责任边界；不并行修改 catalog/schema 与安装索引。
2. 为本地插件作者流程补齐模板、生成目录校验和打包入口，再把现有本地包管理能力接入共享面板。
3. 固定产品目录签名字段、发行来源与 Pro 私有下载授权协议；实现服务端产品级权益授权和客户端 fail-closed 集成。
4. 将远程下载接到既有包验证与项目级原子安装事务，逐步开放 Lite/Core、普通 Peanut 插件和 Pro 的对应发行记录。
5. 完成下载篡改、版本冲突、断网、权限拒绝、Creator 占用、回滚和 Lite Host 重启切换验证后，更新用户文档与 release 流程。

## Open Questions

- 本地创建插件的模板是否需要同时提供 Creator 3.8 Host 扩展模板与普通 Peanut Core 插件模板；首版默认提供这两类已有契约。
- 历史版本默认保留数量与手动清理策略可在 UI 实现阶段依据包体积确定，不改变签名或回滚契约。
