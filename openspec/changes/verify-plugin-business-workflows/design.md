# Design

## Context

动机见 proposal。Lite main 24f80d7 / Pro main 845a26e 已回读远端；Host/Core 发行描述符来自 d79097b。当前 Creator 3.8.7 已运行测试工程。总管登记 self-delivery 主检出例外，标准 linked-worktree preflight 不通过，该限制与例外核对分别留证。

## Goals / Non-Goals

**Goals:** 在真实已安装插件上执行用户指定的业务顺序，直接失败先保存证据再定位；源码修复后重新正式构建、安装并复测。

**Non-Goals:** 不改变紧凑 UI，不修改其他仓、Pro 子模块或公共内核协议，不开展正式产品发布，不把旧截图、单元测试当成未执行链路的成功证明。

## Decisions

1. 串行 DAG：接管和备份 → Host → UI Prefab → SDF → SnowB → 最终交付。四项共用 Creator、活动插件、资源库和安装状态，因此不派并行 Agent。
2. 使用既有 panel bridge 与服务契约；Lite 负责宿主身份和槽位路由，Pro 负责字体与控制器业务。SnowB 的 requestSbfBase64 当前明确抛错，先确认真实发布是否触发，再决定窄适配；不预先重构协议。
3. 独立前缀 plugin-business-20261012；改动前备份规则、安装包、相关资源和设置到设备证据目录。工程写入经过实际 sandbox 审批，禁止复用权限假设。
4. UI 操作走 CUA；文件摘要、原生导入结果及日志与操作一起记录。SDF 根据实际支持项测试，不把纯 mask 服务误当文件字体 UI。
5. 最小失败修复位于所属仓。Pro 尚未发现 OpenSpec root；若需 Pro 源码修改，先核对 adoption 状态及授权门禁，不自动初始化。保持签名、包摘要、调用者身份、路径校验和原包边界断言。
6. 定向验证通过后按仓规则 checkpoint，最终组合 tree 上运行完整 verify；无源码变化且证据精确匹配才复用。最终推送后回读 SHA，GitHub Actions 未核实且不作为验收条件。

## Risks / Trade-offs

- 主检出存在旧构建目录 → 原样保留，不混入提交；主检出例外不扩展到 Hub。
- 原工程可能有未保存编辑 → 先记录并取消已知测试编辑，不丢弃未知内容。
- 导入可能需要 MCP 能力或审批 → 使用正式授权入口；缺能力记录未执行，不绕过安全开关。
- 真实链路失败可能涉及范围外能力 → 留下输入、错误与最小定位后停止依赖步骤，说明扩展范围并取得授权。

## Migration Plan

无持久数据迁移。需要更新时从规范源码构建；Host 更新正常退出并通过工程 npm run creator 重启，Core/插件走正式入口，核对清单与活动身份。失败恢复备份，保留失败日志和测试输入。所有必须链路通过前不宣布业务验收完成，不自动归档。

## 授权补充：原生控制器复绑

用户已明确授权修复 Lite 内核按钮事件绑定的幂等性。真实 MCP 复绑在同一按钮追加了完全相同事件；仅在 lumen Prefab document 合并精确匹配事件引用，保留不同事件和已有条目索引，不改公开协议、权限或 UI。与 Pro 离线实现分别回归，正式 Core 包安装重启后复测。
